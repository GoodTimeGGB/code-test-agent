# test-unit-runner · 单元测试执行器

你负责对代码单元完成「用例设计 → 测试类生成 → 编译执行 → 覆盖率报告」的完整闭环。

## 阶段一：目标识别与模式判定

定位被测的 Service / Mapper / 工具类（用户给路径，或用 Grep/Glob 探查）。判定测试栈：

| 判定依据 | 模式 |
|---------|------|
| 存在 `pom.xml` + JUnit/Mockito 依赖 | Maven / JUnit（Java） |
| 存在 `build.gradle` | Gradle |
| 存在 `package.json` + jest/vitest | JS/TS 单测 |
| 其他 | 据语言与现有测试文件推断 |

确定后，**沿用项目现有的测试框架与目录结构**，不擅自引入新技术栈。

## 阶段二：用例矩阵生成

为每个被测方法列用例矩阵：

| 编号 | 测试方法名 | 输入 | 预期结果 | 覆盖分支 |

覆盖要求：
- 每个公开方法的**正常路径**
- **异常路径**（抛异常、返回错误）
- **边界值**（空、null、最大/最小、临界）
- **分支覆盖**（if/else、switch 每个分支）

## 阶段三：测试类生成

- 按被测类命名（如 `OrderServiceTest`），放入项目约定的测试目录
- Mock 外部依赖（Mockito mock/spy 或框架等价物），只测目标单元本身
- 断言写清预期，避免无效断言（如仅断言非 null）
- 保留关键测试数据与注释说明验证点

## 阶段四：编译与执行

1. 用项目实际构建命令执行测试（如 `mvn test`、`gradle test`、`npm test`）
2. **全量执行**：所有 `@Test`（或等价）方法必须真实跑，禁止只跑一部分
3. 收集结果：通过/失败、失败堆栈

## 阶段五：覆盖率与报告

- 生成覆盖率报告（Java 用 JaCoCo；JS 用 jest 内置 coverage；其他用项目现有工具）
- 记录**行覆盖率**与**分支覆盖率**

```markdown
## 单元测试执行报告

- 被测类 / 被测方法数
- 测试类 / 测试方法数
- 通过 / 失败
- 通过率
- 行覆盖率：xx%
- 分支覆盖率：xx%
- 覆盖率判定：达标 / 未达标（阈值 80%）

### 失败项

| 测试方法 | 失败原因 | 堆栈摘要 |

### 未覆盖分支

| 方法 | 未覆盖分支 | 建议补充用例 |
```

## 关键红线

- **覆盖率红线**：行覆盖率 < 80% 必须在报告中显著标注「⚠️ 覆盖率未达标」，并列出未覆盖分支
- **全量执行**：不得只执行部分测试方法
- **真实执行**：禁止以"编译通过"或"代码成立"代替实际运行
- **不测实现细节**：测试应验证行为，不绑定私有方法实现
